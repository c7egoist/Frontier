# Project-Drive

A **Project-Zero-style project** for the GRIT → Frontier vehicle port: its own `Source/`, `Build/`, `Makefile`,
`Content/` and CMake target, sitting on the shared `Engine/` exactly like `Project-Zero`, `Project-Dyno` and
`Project-Fluid` do. Drop this folder into `Frontier/Projects/` and it builds with the engine's own toolchain.

> Naming: the earlier codename "Project-Tractrix" is retired — this is the clean, plainly-named replica. Rename the
> folder/target if you prefer another word after `Project-`; nothing outside this folder depends on the name.

## Why it mirrors Project-Zero
Project-Zero is a thin project over the shared engine with **three build systems**; Project-Drive keeps the same shape:

| Build path | Project-Zero | Project-Drive |
|---|---|---|
| Windows product (MSVC + Vulkan + Slang) | `Construct.bat` → `Build/ToolchainSequence.ps1` | *(add once GameExecution lands — same driver)* |
| Linux product (CMake + Vulkan + GLFW + ImGui) | top-level `linux-app` preset, `add_executable(Project-Zero …)` | a sibling target in the top-level `CMakeLists.txt` |
| **Headless CPU reference (plain g++, no GPU)** | `Makefile` → `CpuReferenceMain.cpp` | **`Makefile` → `DriveTelemetry` + `SurfelReference`** |

The headless references are what runs in a GPU-less sandbox and what these files deliver **today, building and running**.

## What's here (built + run with plain g++)
```
make run          # builds both, runs them into Diagnostics/
```
- **`Source/DriveCourse.h`** — one definition of the course (checker pad + ramp + 3 speed bumps + 8 cones), read by
  BOTH the physics ground query and the renderer's geometry, so the wheels rest exactly on what's drawn.
- **`Source/DriveTelemetry.cpp`** — drives the **real** ControlVehicle (socket `VehicleGeometry`, XPBD soft tyres,
  Pacejka drivetrain, aero) over the course with **no body collision** (only wheels touch). Writes to `Diagnostics/`:
  - `telemetry.csv` — per 60 Hz frame: chassis pose, speed, engine RPM/gear/boost, and per-wheel load / slip ratio /
    slip angle / steer / spin / contact / brake temperature / ABS.
  - `timing.log` — steps, physics µs/step, real-time factor.
  - `run.log` — a run summary (peak speed, ramp takeoff, airborne time, suspension travel, final X).

  A sample run: settles on the pad → full throttle to **123 km/h** shifting 3→6 → **launches off the ramp** (takeoff
  12.6 m/s, ~0.9 s airborne, wheel load spikes then drops to zero) → lands → brakes and downshifts.
- **`Source/SurfelReference.cpp`** — the **Surfel GI** render path (the split the engine's GTX path and the standalone
  `SurfelGI/` reference use): visibility G-buffer → sharp **direct** light (sun NEE + sky dome) → a persistent field of
  world-space **surfels** carrying temporally-averaged **indirect** bounce through a hash grid (converges, no boil).
  Adds a compact **BVH** over the triangle soup (course + real ControlVehicle shell + procedural wheels). Writes
  `Diagnostics/drive_gi.ppm` + `surfel_timing.log`. ~5.6k triangles, ~11.6k surfels, 800×450 in well under a second.
- **`Source/ControlVehicleMesh.inl`** — the real ControlVehicle exterior (1405 v / 2780 t), generated by
  `CarModelling/Tools/MeshToHeader.py`.

Preview render: `../../../../Exhibits/Gallery/Drive/DriveSceneSurfelGi.png` (surfel GI of the drive scene, generated by `make surfel`).

## Editor integration layer (drivable editor) — landed, compiled against the real engine
These modules plug the vehicle into Frontier's native ImGui editor. Each was compiled against the actual engine
headers (`SceneStructure.h`, `CameraProjection.h`, `InputExchange.h`, `EditorInstance.h`) and the real vehicle
physics, and the physics bridge was run (car drives, wheels track the axles, matrices orthonormal):

| Module | Role | Mirrors |
|---|---|---|
| `Source/VehicleInstanceSequence.{h,cpp}` | live `VehicleSolver` + collider-free chassis → body & 4-wheel `InstanceRecord::World` rows + accel-structure refit | `PhysicsInstanceSequence` |
| `Source/ChaseCameraSolver.{h,cpp}` | player/vehicle camera (spring follow, speed FOV) | `FlyThroughSolver` |
| `Source/DriverInputExchange.h` | `InputExchange` → the existing `DriverInputIntegrator` (W/A/S/D, Space, Shift/Ctrl, R) | — |
| `Source/VehicleInspectorSequence.h` | one `EditorSheet` per subsystem, **all curves editable** (torque, boost, gears, Pacejka, aero) | `EditorInspectorSequence` |

The five `GameExecution.cpp` hooks and the `--scene drive` alias are spelled out in **`Docs/DriveEditorWiring.md`**;
the CMake integration is `Build/ProjectDrive.cmake`.

## Remaining (authoring, not code — you build/drive)
1. `DriveCourse.gltf` + its one-shot `DriveSceneAuthor` exporter (course + body + procedural wheels, instance
   order body=0 / wheels=1..4), the same pattern as `ShowcaseStructure`. All geometry already exists as data.
2. Assign the flake clearcoat material to the body instance, rubber to the wheels.
3. Paste the five hooks from `Docs/DriveEditorWiring.md` into `GameExecution.cpp`.
4. Port the shared Surfel-GI GPU compute route into `Frontier.exe`; the CPU reference here is its oracle.

## Run it
```sh
cd Projects/Project-Drive
make run                       # or: bash Build/ToolchainSequence.sh
#   telemetry.csv / timing.log / run.log / drive_gi.ppm land in Diagnostics/
./bin/SurfelReference --w 1280 --h 720 --frames 48 --rays 12   # higher-quality GI still
```
