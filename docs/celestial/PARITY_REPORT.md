# Project Zero / HTML Celestial Parity Report

**Date:** 2026-09-14  
**Repository:** `c7egoist/Frontier`  
**Reference:** `docs/celestial/index.html` (the checked-in copy of the supplied HTML/WebGL page)  
**Compared engine path:** `Engine/Shaders/ReSTIRViewport.slang`, `Engine/Shaders/AtmosphereScatter.slang`, `Engine/Shaders/CelestialMedia.slang`, `Engine/DisplayPresentation/CelestialSolver.h`, `Engine/DisplayPresentation/CelestialUniform.h`

## 1. Executive conclusion

The Project Zero frames do not look like the HTML reference because the two programs are not rendering the same state through the same presentation contract. The atmosphere march and the coloured dawn complement were ported, but the following higher-level inputs are different:

1. **The sun is in a different place at the same clock time.** The HTML page uses a date-independent, simplified latitude/hour-angle orbit. Project Zero uses a date-, longitude-, UTC-offset-, and ephemeris-based solar solver. The measured elevation error is approximately **1.0–3.7 degrees**, and the azimuth error is approximately **1.3–3.7 degrees**.
2. **The exposure curve is not the HTML exposure curve.** The HTML uses `exp2(uEV + autoEV)` with the default `uEV = 0.4`. Project Zero uses an EV100 photographic curve, converts it to a gain, then the showcase applies an additional `800` relative-unit reconciliation constant. At the low sun positions that determine sunset colour, those gains differ by tens of times.
3. **The HTML's aerial fog is not the engine's aerial fog.** The HTML applies a separate spectral aerial-fog integral to every sky ray. The engine puts atmospheric fog into the shared cloud/local-medium density and multiplies it by the cloud absorption coefficient. With the defaults, the engine's effective fog extinction is **83.3 times weaker** than the HTML value before phase and in-scatter differences are considered.
4. **The HTML controls are not all carried in the GPU record.** `uDawnInt`, `uHLInt`, `uHLAuto`, `uSkyTint`, `uSkyBright`, `uSkyVisible`, and `uAtmoVisible` exist in the reference shader. The engine record does not preserve the dawn/horizon-line control values and currently hardcodes the default dawn/white-line behaviour.
5. **The reference has presentation terms that the engine path does not reproduce exactly.** In particular, the HTML adds a small direct-sun bloom term around the disc and performs its own post exposure, ACES tone map, vignette, and gamma conversion. The engine uses the renderer's exposure dispatch and does not have the same direct-sun bloom term in `CelestialSunDisc`.

Therefore the current output is an approximate port, not a mirror copy. The weak/missing white horizon line and the less vibrant sunset are expected consequences of these mismatches; they are not evidence that the line formula itself was completely lost.

## 2. What causes the white horizon line to disappear or move

The reference line is generated by `dawnGlow()` in `docs/celestial/index.html`:

```glsl
float wlWin = mix(1.,
    smoothstep(-5.5, -2.5, elevDeg)
    * (1. - smoothstep(-.6, .3, elevDeg)),
    uHLAuto);
float lineAz = exp(-pow(dAz / .55, 2.));
float line = exp(-pow(alt / .11, 2.))
            * (.7 + .3 * smoothstep(-.4, 0., alt));
glow += vec3(1., .98, .92) * line * lineAz * wlWin * uHLInt * .45;
```

The engine has the same envelope and colour in `CelestialDawnGlow()` (`Engine/Shaders/ReSTIRViewport.slang`). The line is extremely narrow vertically: its angular falloff is `0.11` degrees, and the line window depends on the **sun elevation**, not just the selected clock label. A clock-time comparison is consequently invalid when the solar models differ.

Measured examples:

- At **05:30**, HTML puts the sun at **−6.73°**, while the engine puts it at **−9.03°**. Both are outside/near the lower edge of the line window, but the engine is further into the dark interval.
- At **06:00**, the simplified HTML orbit is at approximately the horizon while the engine is still roughly **−2.3°**. The HTML line has already handed off to the sun/horizon transition, while the engine can still be inside the line window.
- Near sunset the same error occurs in the opposite direction: the engine reaches a given negative elevation at a different clock time and a different azimuth, so the line is not in the same pixels even if the filenames say “sunset”.

The line is also multiplied by `uHLInt` and controlled by `uHLAuto` in the HTML. Those values are not carried by `CelestialUniform`; the engine currently emits the default-equivalent hard-coded result. This means changing the HTML controls cannot be mirrored by Project Zero, and it also makes later tuning appear ineffective.

Finally, the engine's miss path applies a different aerial-media pass after `CelestialSky()`. A narrow white line can be attenuated or surrounded by a different haze response, even when `CelestialDawnGlow()` itself returns the same linear colour.

## 3. Why sunset and twilight are less vibrant

### 3.1 Solar-direction mismatch

A sunset colour ramp is evaluated at the current sun elevation and at the azimuth facing the sun. A 1–3 degree error is large relative to the transition bands:

- The twilight envelope runs from about **−16° to +6°**.
- The horizon-line handoff is concentrated between approximately **−5.5° and +0.3°**.
- The direct-disc presentation changes across approximately **−1° to +8°**.

The same clock label can therefore sample different colours, different line strength, different direct-sun attenuation, and a different pixel location in the two implementations.

### 3.2 Exposure mismatch compresses sunset chroma

The HTML reference applies:

```glsl
float autoEV = -.35 * smoothstep(-8., -1., elevDeg)
             - 1.00 * smoothstep(-1., 6., elevDeg)
             - .60 * smoothstep(6., 30., elevDeg);
col *= exp2(uEV + autoEV); // default uEV = 0.4
```

Project Zero's solver instead evaluates an EV100 curve, converts it with `1 / (1.2 * 2^EV100)`, and the CPU showcase multiplies the result by `800` to reconcile its relative radiance units. Comparing the two scalar gains at the same elevations gives:

| Sun elevation | HTML multiplier | Engine showcase multiplier (`gain × 800`) | Ratio, engine / HTML |
|---:|---:|---:|---:|
| −6.73° | 1.292 | 48.14 | 37.3× |
| +4.04° | 0.591 | 0.584 | 0.99× |
| +16.10° | 0.442 | 0.264 | 0.60× |
| +63.81° | 0.342 | 0.0361 | 0.11× |
| −8.07° | 1.320 | 104.39 | 79.1× |

This is not a small exposure calibration difference. Around civil and nautical twilight the engine can drive the scene into a much higher linear exposure than the HTML page; ACES then compresses the warm ramp toward pale/white values. In daylight the engine is comparatively darker. The result reads as a less saturated sunset even if the underlying dawn-glow colour is similar.

The production Project Zero path also obtains exposure from `ExposureIntegrator::QueryExposure()`, so this is not limited to the scratch renderer's final PNG conversion.

### 3.3 Atmospheric-fog model mismatch

The HTML uses `applyMedia()` with a separate atmospheric-fog density, spectral Rayleigh/Mie coefficients, HG phase function, and in-scatter. For the default clear-sky settings its atmospheric density is `7e-5` per metre.

The engine's `MediaDensity()` adds that same density to the common medium, but `MediaScatter()` then converts *all* density—including atmospheric fog—using `CloudAbsorptionAndWind.x`, whose default is `0.012`. The resulting effective extinction is:

```text
engine: 7e-5 × 0.012 = 8.4e-7 per metre
HTML:   7e-5
ratio:  HTML / engine = 83.3×
```

Over a 60 km near-horizon path, this is approximately optical depth `4.2` in the HTML model versus `0.0504` in the engine model before the different numerical march, phase, and source terms. The engine therefore does not create the same bright, spectrally coloured horizon veil that the HTML uses to lift and saturate sunrise/sunset.

### 3.4 Direct-sun and final presentation differences

The default sun-disc boost and soft-disc envelope are close to the HTML defaults, but the reference also adds a direct-sun bloom term:

```glsl
float sg = exp(-ang * 40.) * .35
         + exp(-ang * 9.) * .03
         + exp(-ang * 2.5) * .004;
col += sg * uBloom * sunCol * uSunIntensity * .6;
```

The engine's `CelestialSunDisc()` deliberately omits this term and leaves the surrounding effect to the lens-flare path. That changes the immediate neighbourhood of the sun and makes the reference sunset read as more luminous even when the broad atmosphere is similar.

The sun tint also differs numerically because the HTML uses its `kelvinRGB(5800)` approximation while the engine uses a Planckian xy-to-linear-sRGB conversion normalized to unit luminance. At 5800 K, the measured linear RGB values were:

| Component | HTML `kelvinRGB` | Engine normalized black-body tint | Engine / HTML |
|---|---:|---:|---:|
| R | 1.0000 | 1.1085 | 1.1085× |
| G | 0.9521 | 0.9760 | 1.0251× |
| B | 0.9066 | 0.9181 | 1.0127× |

This is secondary to the solar-direction, fog, and exposure differences, but it prevents exact direct-sun parity.

Across this sample set:

- Maximum absolute elevation error: **3.72°**.

- Evening elevation error: approximately **−1.0°**.
- Most azimuth errors: approximately **3–4°**.

The HTML model has no date, longitude, UTC offset, equation of time, or real declination. The engine result uses the configured observation date (2026-09-13 in the current defaults), Benoni longitude/UTC offset, and ephemeris calculations. This is a model-contract difference, not floating-point noise.

| Atmosphere ray/sun march | `atmosphere()` with Rayleigh, Mie, ozone, spherical shell | `AtmosphereScatter` port used by `CelestialSky` | Structurally close, not proven pixel-identical |

## 6. What can and cannot be claimed from the current renders

There is currently **no valid per-pixel parity score**. A browser capture of the HTML reference has not yet been made with the same camera, viewport, sun state, atmosphere controls, exposure, flare, and post-processing settings as the engine image. The existing clear-sky PNGs are useful for checking the engine time sequence, but they are not an exact reference comparison because they use the engine ephemeris, a sun-following showcase camera, engine exposure, and engine presentation.

The numerical solar table and the fog/exposure calculations above are valid code-level comparisons. They are sufficient to explain the observed visual differences, but a final pixel-error number must wait until both implementations render a matched state.

## 7. Required order for a true mirror port

To make the HTML reference the source of truth while preserving the requested clear-sky coverage—pre-dawn, sunrise, morning, noon, afternoon/golden hour, sunset, dusk, and twilight—the next implementation pass should be done in this order:

1. Choose one solar contract. For HTML parity, port the exact simplified `sunDirAt()` behaviour into the engine parity path, or change the HTML page to consume the engine ephemeris. Do not compare only clock labels while the direction models differ.
2. Carry `uDawnInt`, `uHLInt`, `uHLAuto`, `uSkyTint`, `uSkyBright`, `uSkyVisible`, and `uAtmoVisible` through the CPU settings and `CelestialUniform` record.
3. Port the HTML `applyMedia()` atmospheric fog as a separate spectral medium. Do not reuse the cloud absorption coefficient for aerial fog.
4. Match the reference sun colour conversion and direct-sun bloom term, including the default `5800 K`, intensity `22`, angular size `0.53°`, softness `0.25`, and disc boost `12`.
5. Match the HTML exposure/post chain for the reference capture. Keep Project Zero's physical/ephemeris mode available as a separate production mode rather than silently comparing it to the HTML approximation.
6. Capture the same nine clear-sky times with identical camera and post settings, then compute the PNG pixel error. Only after that should clouds and other atmosphere features be reintroduced.

Until these contracts are made identical, changing sample counts or adding more cloud detail cannot make Project Zero a mirror of the HTML reference; it only makes a different renderer more converged.
